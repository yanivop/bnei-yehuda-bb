# מתכנן שיבוץ שחקני נוער – בני יהודה כדורסל

## רקע ומטרה

מנהלת המועדון צריכה לשבץ את שחקני מחלקת הנוער (בנים ובנות) לקבוצות המועדון לעונה הבאה.
הכלי שואב את רשימת השחקנים הרשומים כרגע במחלקת הנוער מאתר איגוד הכדורסל (ibasketball.co.il),
מחשב אוטומטית לאיזו שכבת גיל כל שחקן/ית זכאי/ת בעונה הבאה (כולל זיהוי מקרי גבול/חריגים),
ומאפשר למנהלת לשבץ כל שחקן לקבוצה ספציפית דרך ממשק אינטרנטי, כשההחלטות נשמרות ונגישות מכל מכשיר.

## מקור הנתונים

בדיקה ב-API הציבורי של SportsPress (`/wp-json/sportspress/v2/players`) העלתה שהוא **לא כולל תאריך לידה**.
תאריך הלידה כן מופיע בדף הפרופיל הציבורי החדש של שחקן/ית (פורמט `/player/<hash>/`, לדוגמה
`https://ibasketball.co.il/player/3669c682cead9b25-45521412/`), בתוך `div.data-birthdate`.
הרשימה המלאה של שחקני האגודה (עם קישור לכל פרופיל) נמצאת בדף המועדון
(`https://ibasketball.co.il/club/297-2/`) תחת הטאב "שחקנים" (`div.player-gallery`), ומגיעה מוטמעת
ב-HTML הראשי בלי צורך ב-JS.

לכן שאיבת הנתונים תתבצע ע"י **scraping** (לא קריאות API), בדומה לדפוס הקיים ב-`fetchMatches.js`.

הערה: השמות ותאריכי הלידה כבר חשופים פומבית באתר האיגוד. המידע הפנימי היחיד של המועדון
בכלי הזה הוא **השיבוצים** (החלטות התכנון לעונה הבאה) — וזה המידע היחיד שדורש הגנה.

## ארכיטקטורה

שלושה רכיבים, בהמשך לדפוס הקיים בפרויקט (סקריפט Node + GitHub Action + עמוד סטטי):

1. **`fetchPlayers.js`** — סקריפט Node חדש (ללא תלויות, כמו `fetchMatches.js`):
   - שולף את רשימת השחקנים המלאה מטאב "שחקנים" בדף המועדון (שם + לינק לפרופיל + קבוצה נוכחית).
   - עבור כל שחקן/ית, נכנס לדף הפרופיל (`/player/<hash>/`) ומחלץ: שם מלא, קבוצה נוכחית, ליגה
     נוכחית, תאריך לידה. מגדר נגזר מה-class בגלריית השחקנים בדף המועדון (`class="player data-item
     male"` וכדומה — ערך `male`/`female`).
   - מסנן לפי מחלקת הנוער בלבד: האתר עצמו מתייג ליגות/קבוצות כ"נוער" (U18) מול "בוגרים" (למשל
     טאב עם `data-age="adult"` מול `data-filter="U18"` ותווית "נוער") — הסינון מתבסס על התיוג הזה,
     לא על ניחוש לפי שם הליגה.
   - כותב את הפלט ל-`players.json`.
   - **ריצה חד-פעמית/ידנית בלבד** (`workflow_dispatch`), לא בקרון מתוזמן — הרשימה לא צריכה
     להתעדכן אוטומטית, רק כשיש צורך לאסוף/לאפס אותה.

2. **GitHub Action חדש** (`update-players.yml`) — עוטף את `fetchPlayers.js`, מופעל ידנית בלבד
   דרך GitHub UI, מ-commit את `players.json` בהרצה מוצלחת. מבנה זהה ל-`update-report.yml` הקיים,
   רק בלי `schedule:`.

3. **עמוד סטטי חדש** (`squad-planner.html`) — אפליקציית לקוח (HTML+JS רגיל, כמו שאר האתר) שקוראת
   את `players.json` הסטטי, ומתחברת ל-**Firebase** (פרויקט קטן וייעודי) עבור כל מה שדינמי/נערך:
   - **Firebase Auth** (Email+Password) עם **חשבון אחד משותף** קבוע מראש. מבחינת המנהלת זה נראה
     כמו מסך "הזן סיסמה" בלבד (בלי שם משתמש גלוי), אבל מאחורי הקלעים זה מייצר סשן Auth אמיתי,
     שמאפשר אכיפה אמיתית ב-Firestore Security Rules (בניגוד ל-PIN שנבדק רק בצד לקוח וניתן לעקיפה).
   - **Firestore** לנתונים הניתנים לעריכה (ר' "מודל הנתונים" למטה).
   - העמוד **לא יקושר** מ-`index.html`/`report.html` הציבוריים — רק קישור ישיר יגיע למי שצריך.

### שיקולי אבטחה (הוחלט)

- ה-repo ציבורי, ולכן קונפיגורציית Firebase (`apiKey` וכו') וכתובת ה"אימייל" הקבוע **יהיו גלויות
  בקוד** — זה תקין ומקובל: ההגנה של Firebase היא ברמת Firestore Rules, לא בהסתרת ה-`apiKey`.
  הסיסמה עצמה **לעולם לא נכתבת לקוד/ל-repo** — רק מוקלדת ע"י המנהלת בזמן ריצה.
- מאחר שה"שם משתמש" גלוי לכולם, הסיסמה היא קו ההגנה היחיד. Firebase חוסם ניסיונות brute-force
  חוזרים אוטומטית, כך שסיסמה סבירה (לא חייבת סיסמה ארוכה מאוד, ראה החלטת המשתמש) מספיקה כאן,
  בהתחשב בכך שהעמוד לא מפורסם/מקושר ושמידע רגיש (תאריכי לידה) כבר חשוף במקור הציבורי ממילא.
  הדבר היחיד שבאמת מוגן הוא השיבוצים הפנימיים.
- Firestore Rules ידרשו `request.auth != null` גם לקריאה וגם לכתיבה של `assignments`, `config`,
  `manualPlayers`, `playerOverrides`.
- חולשה ידועה ומקובלת: חשבון משותף אחד = אין audit trail של "מי שינה מה", וכל מי שהסיסמה מגיעה
  אליו מקבל גישה מלאה. התקבל כסביר בהיקף הפרויקט.
- לא ננקטו Firebase App Check / reCAPTCHA — נשקלו ונדחו כתוספת מורכבות שלא משתלמת מול האיום
  הריאלי כאן.

## מודל הנתונים

### `players.json` (קובץ סטטי, מיוצר ע"י הסקריפט)

```json
{
  "id": "3669c682cead9b25-45521412",
  "fullName": "אב ירימישין",
  "firstName": "אב",
  "lastName": "ירימישין",
  "currentTeams": ["בני יהודה באהבה"],
  "currentLeague": "ארצית נשים מרכז",
  "birthDate": "1986-10-26",
  "gender": "F",
  "profileUrl": "https://ibasketball.co.il/player/3669c682cead9b25-45521412/"
}
```

פיצול שם פרטי/משפחה הוא היוריסטי (מילה ראשונה = פרטי, שאר המילים = משפחה) — לא מדויק לשמות
מורכבים/שמות משפחה מרובי-מילים; ניתן לתיקון ידני דרך `playerOverrides`.

### אוספי Firestore (מוגנים בסיסמה)

- **`manualPlayers`** — שחקנים שנוספו ידנית ע"י המנהלת (מבנה זהה ל-`players.json` + `manual: true`),
  למקרה ששחקן חסר ברשימה שנשאבה.
- **`playerOverrides`** — מקש לפי `player id`, לתיקון/הסתרת שחקן קיים (למשל תאריך לידה שגוי,
  שם שגוי, או שחקן שעזב את המועדון — `hidden: true`).
- **`config/eligibility`** — טבלת שכבות גיל, נפרדת לבנים ולבנות, ניתנת לעריכה במסך הגדרות:
  ```json
  {
    "boys": {
      "brackets": [
        {"id": "neurim-a", "label": "נערים א׳", "referenceBirthYear": 2011, "exceptionQuota": 3},
        {"id": "neurim-b", "label": "נערים ב׳", "referenceBirthYear": 2012, "exceptionQuota": 3}
      ]
    },
    "girls": { "brackets": [ ... ] }
  }
  ```
- **`config/teams`** — רשימת קבוצות המועדון לעונה הבאה, per שכבה (יכולה להיות יותר מקבוצה אחת
  לשכבה):
  ```json
  [
    {"id": "neurim-a-1", "bracketId": "neurim-a", "label": "נערים א׳ 1"},
    {"id": "neurim-a-2", "bracketId": "neurim-a", "label": "נערים א׳ 2"}
  ]
  ```
- **`assignments`** — מקש לפי `player id`:
  ```json
  {"teamIds": ["neurim-a-1"], "exceptionApproved": false, "note": ""}
  ```
  `teamIds` הוא מערך של 0–2 פריטים, כדי לתמוך במקרי "רישום כפול" (שחקן ששובץ בפועל לשתי קבוצות
  בו-זמנית — קורה לפעמים ולגיטימי).

## לוגיקת זכאות לשכבת גיל

לכל שחקן/ית, לפי חודש/שנת לידה, מול טבלת השכבות של המגדר המתאים:

- **שכבה טבעית**: השכבה שה-`referenceBirthYear` שלה שווה לשנת הלידה.
- **גישור אוטומטי (לא נספר כחריג)**: נולד/ה בדצמבר → זכאי/ת *גם* לשכבה הבוגרת הבאה
  (`referenceBirthYear` הבא), ללא צריכת מכסת חריגים.
- **מועמד/ת לחריג**: נולד/ה בספטמבר–נובמבר (כולל) → יכול/ה *להיות מוצע/ת* לשכבה הבוגרת הבאה,
  מסומן/ת "חריג" ונספר/ת מול `exceptionQuota` של אותה שכבה.

חוקי הזכאות של בנות מבוססים על **אותו עיקרון** (שנת לידה + גישור דצמבר + חריגי ספט-נוב), אך
עם פרטים (שנות ייחוס, מכסות) שיכולים להיות שונים — ולכן `config/eligibility` מפריד `boys`/`girls`
לחלוטין ולא מניח ערכים משותפים.

הממשק **לא חוסם** שיבוץ ידני לכל קבוצה אחרת אם המנהלת בוחרת בכך — רק מציג אזהרה רכה (למשל
חריגה ממכסת חריגים) — כדי לאפשר שיקול דעת ומקרי קצה אמיתיים שהחוקים לא צופים.

## מסכי המשתמש

1. **מסך כניסה** — שדה סיסמה בלבד, בלי שם משתמש גלוי.
2. **מסך תכנון** — מאגר שחקנים מקובץ לפי שכבת גיל זכאית (טבעית + מועמדי חריג/גישור), עם באדג'
   "חריג" ומונה ניצול מכסה לכל שכבה. שיבוץ שחקן לקבוצה ספציפית של השנה הבאה (עד 2 קבוצות).
3. **מסך לפי קבוצות** — קבוצות השנה הבאה כעמודות/כרטיסים, עם רשימת המשובצים לכל קבוצה ומונה
   (X / קיבולת אם רלוונטי).
4. **מסך הגדרות** — עריכת טבלת השכבות/שנות-ייחוס/מכסות לכל מגדר, ועריכת רשימת קבוצות השנה הבאה.
